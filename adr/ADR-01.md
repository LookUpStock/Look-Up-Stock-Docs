# ADR-01: Architekturstil

| Feld | Inhalt |
|---|---|
| **Titel und Nummer** | ADR-01: Architekturstil |
| **Status** | entschieden; **teilweise abgelöst durch ADR-07** (27.10.2026): Seit Sprint 5 besteht das Backend aus zwei Diensten (core-service, marktdaten-service). Die Drei-Schichten-Architektur gilt innerhalb jedes Dienstes weiter; die Anwendung als Ganzes ist kein einzelnes Backend mehr. |
| **Kontext** | LookUpStock soll Anlagen suchen, Portfolios verwalten und Monte-Carlo-Simulationen berechnen. Folgende Anforderungen und Randbedingungen spielen eine Rolle:<br>• Die Simulation ist rechenintensiv und muss 10.000 Pfade in höchstens 3 s berechnen (NF-01); sie soll daher auf dem Server laufen.<br>• Der API-Key der Finanzdaten-API darf nicht an den Browser gelangen (NF-06).<br>• Die Kernlogik muss automatisiert testbar sein (NF-11).<br>• Frontend und Backend liegen in getrennten Repositories und werden parallel von verschiedenen Teammitgliedern entwickelt.<br>• Das Projekt wird auch in der Webprogrammierung bewertet, die ein eigenständiges Frontend vorsieht. |
| **Betrachtete Alternativen** | **A: Serverseitig gerenderte Anwendung** (Spring Boot mit Thymeleaf, Oberfläche und Logik in einer Anwendung)<br>+ nur eine Anwendung, keine Schnittstelle zu entwerfen<br>– Oberfläche und Logik eng verzahnt, Logik schwerer isoliert testbar<br>– passt nicht zu den getrennten Repositories und den Anforderungen der Webprogrammierung<br><br>**B: Drei-Schichten-Architektur mit getrenntem Frontend**<br>+ klare Trennung der Verantwortlichkeiten, jede Schicht einzeln austauschbar und testbar<br>+ Frontend und Backend können parallel über eine abgestimmte REST-Schnittstelle entwickelt werden<br>– Schnittstelle muss entworfen, dokumentiert und gepflegt werden<br>– zwei Anwendungen müssen gebaut und bereitgestellt werden<br><br>**C: Microservices** (eigene Dienste z. B. für Portfolio, Simulation und Marktdaten)<br>+ Dienste unabhängig skalier- und austauschbar<br>– für vier Personen und acht Wochen zu aufwendig: mehrere Deployments, Kommunikation zwischen Diensten, verteilte Fehlerbehandlung |
| **Entscheidung** | Wir wählen **Alternative B: Drei-Schichten-Architektur**.<br>• **Präsentationsschicht:** Frontend aus HTML, CSS und JavaScript im Browser sowie die Spring-REST-Controller im Backend, die HTTP-Anfragen annehmen und JSON zurückgeben.<br>• **Logikschicht:** Services und Fachklassen (u. a. Simulations-Engine) mit der gesamten Anwendungslogik.<br>• **Datenschicht:** Repositories für den Zugriff auf die PostgreSQL-Datenbank sowie der Zugriff auf die externe Finanzdaten-API.<br>Jede Schicht nutzt nur die direkt darunterliegende. Innerhalb der Schichten ist der Code nach Fachbereichen (Anlagen, Portfolio, Simulation) gegliedert. Das entspricht *High Cohesion*; die Kommunikation ausschließlich über die nächste Schicht sorgt für *Low Coupling*. |
| **Konsequenzen** | **Einfacher:** Die Logik ist ohne Oberfläche und ohne HTTP testbar; Frontend und Backend können parallel entwickelt werden; Aufgaben lassen sich entlang von Schichten und Fachbereichen verteilen.<br>**Schwieriger:** Jede Änderung an der Schnittstelle betrifft Frontend und Backend; es gibt zwei Build- und Deployment-Prozesse.<br>**Betroffene Artefakte:** Klassendiagramm (Aufteilung der Klassen auf die Schichten), Sequenzdiagramme, API-Design, CI-Pipelines für Backend und Frontend. |
