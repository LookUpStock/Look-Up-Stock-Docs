# ADR-07: Getrennte Dienste und asynchrone Kommunikation

| Feld | Inhalt |
|---|---|
| **Titel und Nummer** | ADR-07: Getrennte Dienste (core-service, marktdaten-service) und asynchrone Kommunikation über eine Queue (technische Story Docs #158) |
| **Status** | entschieden (Umsetzung in BE #105, #106, #107, #114). Löst ADR-01 teilweise ab: Die Drei-Schichten-Architektur gilt weiter innerhalb jedes Dienstes, die Anwendung als Ganzes ist kein einzelnes Backend mehr. |
| **Datum / Sprint** | 27.10.2026 / Sprint 5 |
| **Kontext** | Bisher ist das Backend eine einzige Spring-Boot-Anwendung (ADR-01). Microservices wurden damals als zu aufwendig verworfen.<br>Neue Anforderungen und Randbedingungen:<br>• Portfolio-Guidelines Webprogrammierung (Abgabe 08.11.2026): Der Web-Service folgt „composable architecture“ bzw. MACH; monolithische Architekturen werden nicht akzeptiert. Die Kommunikation zwischen den Komponenten erfolgt asynchron, begründete Ausnahmen sind zugelassen. Bewertet werden außerdem die Integration des Fremdservices („Asynchronität wird eingehalten“) und die Infrastruktur-Optimierung (Queue, Cache u. a.).<br>• Change Request CR-01 (US-11, US-12): Nutzungsereignisse werden anonym erfasst (E36, E37). Die Erfassung darf eine Simulation weder verlangsamen noch scheitern lassen.<br>• NF-01: Eine Simulation mit 10.000 Pfaden braucht die Kursdaten aller Anlagen, bevor sie rechnen kann. NF-07: Fällt Twelve Data aus, werden Kurse jünger als 24 h aus dem Cache verwendet. NF-12: Kursdaten nur über die Schnittstelle `MarketDataProvider`.<br>• Die Trennstelle existiert im Code schon: Alle Kursdaten laufen über `MarketDataProvider` (NF-12) und `PriceHistoryService`.<br>• Rahmen: vier Personen, eine Woche (Sprint 5), Heroku mit einer PostgreSQL-Datenbank, keine zusätzlichen Kosten. Alle Tests müssen weiter ohne Internet laufen (NF-12), die Abdeckung der Kernlogik bleibt über 80 % (NF-11). |
| **Betrachtete Alternativen** | **Schnitt der Dienste**<br>**A1: Ein Dienst je Fachbereich** (Anmeldung, Portfolio, Simulation, Vergleich, Marktdaten, Auswertung)<br>+ maximale Trennung<br>– sechs Deployments, viele Aufrufe zwischen Diensten, verteilte Transaktionen zwischen Portfolio und Simulation; in einer Woche nicht machbar<br><br>**A2: Zwei Dienste: core-service und marktdaten-service**<br>+ Der Schnitt liegt an der vorhandenen Schnittstelle `MarketDataProvider`; Kernlogik, Tests und Datenmodell des Core bleiben unverändert<br>+ Die Integration von Twelve Data (API-Key, Fehlerzuordnung, Caches) ist an einer Stelle gekapselt und unabhängig austauschbar<br>– Die Simulation muss den marktdaten-service aufrufen, bevor sie rechnen kann<br><br>**A3: Simulation als eigener Dienst**<br>+ rechenintensiver Teil getrennt skalierbar<br>– Simulation braucht Portfolio, Kurse und Speichern; drei Dienste müssten zusammenarbeiten, ADR-05 (Vergleich nutzt `SimulationService.run`) müsste umgebaut werden<br><br>**Asynchrone Kommunikation**<br>**B1: Message Broker als Heroku-Add-on (z. B. RabbitMQ)**<br>+ verbreitete Lösung, eigene Infrastruktur-Komponente<br>– zusätzlicher Dienst mit eigenen Zugangsdaten, Kosten und Verfügbarkeit des Tarifs ungewiss, neue Bibliothek und Einarbeitung; Tests bräuchten einen Broker oder eine Attrappe<br><br>**B2: Queue-Tabelle in der gemeinsamen PostgreSQL-Datenbank**<br>Nachrichten werden als Zeilen geschrieben; Verbraucher holen sie mit `SELECT … FOR UPDATE SKIP LOCKED` in festen Abständen ab und löschen sie nach erfolgreicher Verarbeitung.<br>+ keine zusätzlichen Kosten oder Zugangsdaten, Nachrichten überstehen Neustarts der Dynos<br>+ mit der vorhandenen Test-Datenbank der CI testbar<br>– Polling statt Push, Verzögerung von einigen Sekunden; Last auf der Datenbank (bei der erwarteten Nutzung unkritisch)<br><br>**B3: Nur innerhalb eines Dienstes asynchron** (`@Async`, Spring-Events)<br>+ kaum Aufwand<br>– keine Kommunikation zwischen Komponenten; erfüllt die Vorgabe nicht, Nachrichten gehen bei einem Neustart verloren |
| **Entscheidung** | Wir wählen **A2 (zwei Dienste)** mit **B2 (Queue-Tabelle in PostgreSQL)**.<br><br>**core-service** (bisheriges Backend): Anmeldung, Portfolios, Simulation, Vergleich, gespeicherte Simulationen, Beispielsimulation, REST und GraphQL, Auswertungen (US-11, US-12). Er ist der einzige Ansprechpartner des Frontends. Die Tabelle `asset` bleibt im Core, weil Portfolios auf sie verweisen.<br>**marktdaten-service** (neu): Anbindung an Twelve Data, Such-Cache und Kurs-Cache. Endpunkte nur für den core-service, z. B. `GET /internal/search?q=` und `GET /internal/monthly-prices/{symbol}?mic=`, geschützt mit einem internen Schlüssel im Header `X-Internal-Api-Key`. Der Kurs-Cache liegt im eigenen Schema `marktdaten` und wird über Symbol und MIC-Code statt über die `asset.id` angesprochen. Kein Zugriff auf die Tabellen des Core.<br><br>**Synchrone Ausnahme:** Kursabfrage und Suche vom Core an den marktdaten-service laufen synchron über HTTP (`MarktdatenClient implements MarketDataProvider`, Spring `RestClient`, Timeout 5 s). Begründung: Die Simulation braucht die Kurse, bevor sie rechnen kann (NF-01), und der Nutzer wartet bei der Suche auf die Treffer. Ist der marktdaten-service nicht erreichbar, antwortet der Core wie bisher mit `503 UPSTREAM_UNAVAILABLE` (NF-07).<br><br>**Asynchron über die Queue** (Tabelle `queue_message`: Thema, Inhalt als JSON, Zeitpunkt):<br>• **`nutzung.ereignis`** (US-11): Nach einer erfolgreichen Aktion (E37) legt der auslösende Dienst ein Ereignis mit Art und Zeitpunkt in die Queue (E36), ohne auf die Verarbeitung zu warten. Ein Verbraucher im Auswertungsteil des Core überträgt die Ereignisse in die Tabelle der Nutzungsereignisse. Schlägt das Einstellen fehl, wird das protokolliert; die eigentliche Aktion bleibt erfolgreich.<br>• **`kursdaten.vorladen`** (Verfügbarkeit, NF-07): Wird ein Portfolio angelegt oder geändert, legt der Core eine Nachricht mit Symbol und MIC-Code der Anlagen in die Queue. Der marktdaten-service lädt fehlende oder veraltete Kurse im Hintergrund in seinen Cache. Die nächste Simulation findet die Kurse dann meist schon im Cache vor.<br><br>**Technik der Queue:** Schnittstelle `MessagePublisher` (Einstellen) und je Thema ein Verbraucher mit `@Scheduled` (alle 5 s, höchstens 50 Nachrichten). Verarbeitet wird mit `FOR UPDATE SKIP LOCKED`, damit mehrere Instanzen keine Nachricht doppelt holen; nach drei Fehlversuchen wird eine Nachricht als fehlgeschlagen markiert und nicht weiter versucht. Die Schnittstelle erlaubt später einen Wechsel auf einen Message Broker (B1), ohne die Aufrufer zu ändern.<br><br>**Repository und Betrieb:** Ein Repository mit zwei Ordnern (`core-service/`, `marktdaten-service/`), zwei Heroku-Apps (Monorepo-Buildpack mit `APP_BASE`), eine gemeinsame PostgreSQL-Datenbank mit getrennten Schemas (`public` für den Core, `marktdaten` für den marktdaten-service; `queue_message` im Core-Schema). Jeder Dienst hat eigene Flyway-Migrationen und eine eigene CI mit Pfadfiltern. Der API-Key von Twelve Data liegt nur noch beim marktdaten-service, der interne Schlüssel bei beiden, jeweils nur in den Heroku-Konfigurationsvariablen.<br><br>**Reihenfolge:** zuerst ein reiner Verschiebe-PR nach `core-service/` (BE #105), dann marktdaten-service (BE #106), zweite Heroku-App und CI (BE #107); die Queue (BE #114) parallel im Core. Migrationen im Core: V9 Nutzungsereignisse und Rolle (BE #110), V10 Queue (BE #114), V11 Entfernen der alten Tabelle `price_history` nach dem Umzug des Kurs-Caches (BE #106).<br><br>**GRASP-Bezug:**<br>• *Protected Variations / Indirection:* `MarketDataProvider` und `MessagePublisher` verbergen, ob Kurse lokal, über HTTP oder von Twelve Data kommen und ob die Queue eine Tabelle oder ein Broker ist.<br>• *High Cohesion / Low Coupling:* Jeder Dienst hat einen klaren Zweck; der Core kennt vom marktdaten-service nur zwei Endpunkte, der marktdaten-service den Core gar nicht.<br>• *Controller:* Die Use-Case-Controller (ADR-02, ADR-05) bleiben im Core unverändert. |
| **Konsequenzen** | **Einfacher:**<br>• Die Integration von Twelve Data ist an einer Stelle gekapselt; ein Anbieterwechsel betrifft nur den marktdaten-service (NF-12).<br>• Erfassung der Nutzung und Vorladen der Kurse laufen entkoppelt; die Antwortzeit der Simulation bleibt unverändert, häufig wird sie durch den vorgeladenen Cache kürzer.<br>• Die Anforderungen der Webprogrammierung (kein Monolith, asynchrone Kommunikation, Queue) sind erfüllt, ohne Kernlogik und Tests des Core umzubauen.<br><br>**Schwieriger:**<br>• Zwei Deployments mit eigener Konfiguration; der Core startet zwar ohne den marktdaten-service, Suche und Simulation liefern dann aber 503.<br>• Die Ereignisse erscheinen mit einigen Sekunden Verzögerung im Dashboard; Ereignisse kurz vor Monatsende können deshalb erst im neuen Monat verarbeitet werden. Gezählt wird der Zeitpunkt der Aktion, nicht der Verarbeitung (E38).<br>• Die gemeinsame Datenbank bleibt eine Kopplung; beide Apps teilen sich die Verbindungen der Heroku-Datenbank (Pool je App auf höchstens 5 Verbindungen begrenzen).<br>• Der Kurs-Cache wird beim Umzug neu aufgebaut; die ersten Simulationen danach rufen Twelve Data erneut ab.<br>• Neue Tests: `MarktdatenClient` (Antworten, Timeout, 503), Queue (Einstellen, Abholen, Wiederholung, Ausfall), marktdaten-service (Endpunkte, interner Schlüssel).<br><br>**Betroffene Artefakte:**<br>• ADR-01 (Status „teilweise abgelöst durch ADR-07“)<br>• Klassendiagramm v6, ER-Diagramm v6, Domänenmodell v5 (Docs #163)<br>• API-Design: interne Endpunkte des marktdaten-service, Abschnitt „Auswertungen“ (Docs #165)<br>• README beider Dienste, CI-Workflows, Heroku-Konfiguration (BE #105, #107)<br>• Testkonzept Version 5 (Docs #167)<br>• Change Request CR-01, Abschnitt 5.3: Ort der Ereigniserfassung ist hiermit entschieden (Docs #166) |
