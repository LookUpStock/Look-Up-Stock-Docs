# ADR-02: Controller für den Use-Case Simulation durchführen

| Feld | Inhalt |
|---|---|
| **Titel und Nummer** | ADR-02: Controller für den Use-Case Simulation durchführen (US-04) |
| **Status** | entschieden |
| **Kontext** | Festzulegen ist, welches Objekt unterhalb der UI-Schicht das Systemereignis „Simulation durchführen“ empfängt und die zugehörige Systemoperation koordiniert. Die Systemoperation umfasst: Portfolio laden, historische Kursdaten beschaffen, Rendite und Volatilität schätzen, Wertverläufe simulieren und das Ergebnis aufbereiten.<br>Anforderungen und Randbedingungen:<br>• Nach ADR-01 gehören die REST-Controller zur Präsentationsschicht; sie sollen nur HTTP und JSON behandeln.<br>• Die Ablauflogik soll ohne HTTP testbar sein (NF-11).<br>• Der Vergleich (US-07) soll dieselbe Ablauflogik später wiederverwenden können. |
| **Betrachtete Alternativen** | **A: Der REST-Controller `SimulationController` koordiniert selbst**<br>+ wenige Klassen, kurzer Weg vom Request zum Ergebnis<br>– Ablauflogik an HTTP gebunden und nur mit laufendem Web-Server testbar<br>– Präsentations- und Logikschicht vermischt, widerspricht ADR-01<br>– für den Vergleich nicht wiederverwendbar<br><br>**B: Fassaden-Controller für das gesamte System** (ein Objekt, z. B. `LookUpStockFacade`, empfängt alle Systemoperationen)<br>+ ein einziger Einstiegspunkt in die Logikschicht<br>– wächst mit jedem Use Case und wird unübersichtlich (niedrige Kohäsion)<br>– mehrere Personen arbeiten gleichzeitig an derselben Klasse<br><br>**C: Use-Case-Controller `SimulationService`** in der Logikschicht<br>+ ein klar abgegrenztes Objekt je Use Case mit hoher Kohäsion<br>+ ohne HTTP direkt in Unit-Tests aufrufbar<br>+ vom Vergleich wiederverwendbar<br>– eine zusätzliche Klasse zwischen REST-Controller und Fachklassen |
| **Entscheidung** | Wir wählen **Alternative C**: Der **`SimulationService`** ist nach GRASP der *Controller* für den Use-Case „Simulation durchführen“.<br>• Der `SimulationController` (Präsentationsschicht) nimmt `POST /api/v1/simulations` an, wandelt den Request um und ruft `SimulationService.simulate(...)` auf.<br>• Der `SimulationService` empfängt diese Systemoperation und koordiniert die Schritte: Portfolio über den `PortfolioService` laden, Kursdaten über den Marktdaten-Zugriff beschaffen, Parameter mit dem `ParameterEstimator` schätzen, die `MonteCarloEngine` aufrufen und das Ergebnis mit dem `MetricsCalculator` aufbereiten.<br>• Der `SimulationService` rechnet nicht selbst, sondern delegiert an die jeweils zuständigen Klassen.<br>Die übrigen Use Cases folgen demselben Muster (z. B. `PortfolioService` für „Portfolio erstellen“). |
| **Konsequenzen** | **Einfacher:** Der Ablauf einer Simulation lässt sich mit Unit-Tests ohne Web-Server prüfen; der Vergleich (US-07) kann den `SimulationService` wiederverwenden; die REST-Controller bleiben schlank.<br>**Schwieriger:** Eine zusätzliche Aufrufebene; im Code-Review muss darauf geachtet werden, dass keine Ablauflogik in die REST-Controller wandert.<br>**Betroffene Artefakte:** Klassendiagramm (`SimulationController`, `SimulationService`), Sequenzdiagramm US-04 (Kennzeichnung *Controller* am `SimulationService`), Unit-Tests der Simulationslogik. |
